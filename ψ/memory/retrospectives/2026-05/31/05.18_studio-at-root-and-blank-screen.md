## Honest Feedback (session-specific)
1. **Four redeploys of one worker in 30 min** with `index.html` at `max-age=3600` is a blank-screen generator for anyone mid-session — I never paused to consider the cache implication of rapid iteration on a live domain.
2. **The "app.buildwithoracle.com:47778" report was ambiguous** (stale bundle cache vs stored host) and cost a round to pin down; I shipped the self-heal (covers stored-host) but the cache angle was the real first-reload culprit.
3. **dev-browser lifecycle churn** — I started/stopped the standalone server three times this session; each teardown left a "Connecting…" stall for the user. Should have left it persistent during active browser work.

## Lessons Learned (generalizable)
- **An SPA's HTML entry must be served `no-cache` / `must-revalidate` when assets are content-hashed + immutable.** Otherwise a reload within the HTML's cache window after a deploy serves a stale `index.html` pointing at a purged JS hash → blank white screen. This is the #1 SPA-on-CDN deploy footgun.
- **A `curl`/HTTP-200 check cannot observe a stale *browser* cache.** After a deploy that rotates asset hashes, the failure mode lives inside already-open browsers, not in a fresh request. To verify "existing users can reload," you must reload a previously-loaded browser session, not curl the URL.
- **Leave a shared dev-tool server (dev-browser) running for the duration of active browser work** instead of start/stop per use — repeated teardown surfaces as connection stalls.
